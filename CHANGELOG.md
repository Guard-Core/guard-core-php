# Release Notes

v4.3.0 (2026-10-01)
-------------------

The safety-corpus release: guard-core-php 4.3.0 tracks the guard-core 4.3.0 release. The engine gains the spec 12 event bus with dynamic rules and Redis-backed metrics persistence, the spec 10 geo download and refresh lifecycle, the spec 04 ReDoS safety gates over PCRE plus the performance monitor, and the three new spec 4.1.0 conformance runners (pattern_safety, events, redis_interop) with fail-closed xfail baselines; the whole suite now sits behind a 100%-line coverage gate (every executable line covered or provably unreachable), and the hex-escape attack indicator carries the reference's parity backslash again, unbreaking PHP 8.5's stricter PCRE2.

Event bus, metrics collector, and dynamic rules (spec 12)
----------------------------------------------------------

### Added

- **The spec 12 parity port: EventBus, EventFilter, MetricsCollector, SecurityMetric, DynamicRuleManager and DynamicRules land engine-side, with the SecurityConfig agent gating (`agent_enable_events` / `agent_enable_metrics`, both default true) and the new `dynamic_rules_cache_path` field.** Ported from the reference event-bus surface at the spec 12 parity commit (PR #43, cherry-pick of 136f35b); both new suites are registered in the CI test steps and the coverage collect list. Coverage lives in the new `bin/test_event_bus.php` honesty runner (136 checks at the port).
- **Metrics persist across requests via Redis, closing the last metrics gap: the spec 12 event bus is queueable, but MetricsCollector was in-memory only, so under the shared-nothing runtime model metrics emitted with no agent handler died with the request (PR #48).** The collector's queueing ports onto the reference key semantics (spec 08 namespaced grammar, full_key = prefix + namespace + ':' + key): with no agent handler and a wired RedisHandler the pending backlog lives under `{prefix}metrics:pending` as a JSON list of SecurityMetric payloads (timestamp ATOM, metric_type, value, tags). `setAgentHandler()` dispatches the in-memory queue, then flushes the persisted backlog in order and clears the key, and `drain()` absorbs the persisted backlog too, so FPM adapters can deliver it themselves. Failure arms stay fail-closed and quiet: a corrupted or non-list payload is discarded with a log (empty backlog, never raised), malformed entries are skipped individually with a log, and Redis write failures log and never raise; `agent_enable_metrics` and the EventFilter gate before anything persists, and a disabled RedisHandler falls back to the in-memory queue. `bin/test_event_bus.php` grows the persistence arms (150 -> 174 assertions): backlog accumulation across two sends, flush-on-attach with value/tags/timestamp round trip plus key clearing, drain absorption and empty-drain, redis write failure, corrupted/non-list/scalar pending payloads, malformed-entry skipping with tag coercion, the enable gate, and the disabled-redis fallback; every new MetricsCollector line is executed with a behavioral assertion.

Hex-escape attack indicator parity
-----------------------------------

### Fixed

- **One backslash restored in `Preprocessor::ATTACK_INDICATORS` (PR #50, fixes #49): the hex-escape indicator now carries the escaped-backslash sequence the Python reference uses (two backslash characters plus x in the runtime string), so it matches literal hex-escape text instead of feeding PCRE2 a bare `\x` escape.** The single backslash made PCRE2 see the `\x` escape, accidentally matching NUL-plus-hex on old PCRE2, nearly the opposite of the intent; PHP 8.5's bundled PCRE2 rejects the bare `\x` outright, so `extractAttackRegions` threw `PregFailure` on any such payload and `bin/test_binary_noise_gate.php` fataled (exit 2) on php 8.5.11 while the CI matrix (8.2-8.4) stayed green. On php 8.5.11 the gate runner is back to 80/80 (was a fatal), and `extractAttackRegions` regions literal hex-escape text plus adjacent injections, matching the reference's region behavior.

Behavior rules
--------------

### Added

- **Behavior rules: the engine now runs the reference behavioral surface instead of leaving it out.** Ported from guard_core `_security_config_fields.py` (the behavior fields), `_security_config_field_validators.py` (`BehaviorRuleConfig` and the fail-closed scan validation), `handlers/behavior_handler.py` (sliding windows), `handlers/_behavior_action_dispatch.py`, `handlers/_behavior_response_pattern.py`, `handlers/_behavior_json_pattern.py` and `core/behavioral/processor.py`, structurally following guard-core-go #26. Config surface: `globalBehaviorRules` (rules applied to every route, in addition to any route-specific rules), `behaviorScanResponseBody` (default off: zero behavior change unless enabled) and `behaviorMaxResponseBodyInspectBytes` (default 262144, the reference ge/le bounds 1024..10485760, a configured 0 normalizes to the default). Rule validation mirrors the pydantic constraints fail-closed at construction: `rule_type` in usage/return_pattern/frequency, `threshold` >= 1, `window` default 3600 (a configured 0 falls back), `action` in ban/log/throttle/alert defaulting to log, `ban_duration` >= 1 or null, and the reference's fail-closed return_pattern check: a body-reading (non-status:) pattern with the scan flag off fails construction with the reference message, because the rule would silently never match; `with()` re-validates the copy. Route surface: `RouteConfig` accepts `behaviorRules` (the reference `route_config.behavior_rules`), entries failing the constraints silently dropped (decorator-time leniency like the other route maps). Request side: `GuardEngine::execute` runs usage/frequency rules on requests the pipeline allowed (the reference's process_usage_rules), tracking through sliding windows that are strictly-greater than the threshold, backed by Redis when enabled over the shared key layout (`behavior_usage`/`behavior_returns` namespaces with SHA-256 identity-segment hashing exactly like `_hash_identity_segment`, so the Python and PHP engines share keys) and by bounded local maps otherwise (10,000 endpoint buckets and client rows, oldest-tracked eviction standing in for Python's LRU), failing closed on Redis errors unless `redisFailOpen`. Response side: the new `GuardEngine::processResponse($request, $response)` runs the route's and the config's return_pattern rules for an adapter's outgoing pass-through response, mirroring the reference response factory's behavioral phase; return rules never modify the response. Pattern surface: `status:<code>` matches on status_code alone, `json:<path>==<expected>` walks decoded JSON with case-insensitive comparison and a `[]` segment matching any array element, `regex:<pattern>` matches case-insensitively, and a bare substring matches case-insensitively; body patterns read at most the leading `behaviorMaxResponseBodyInspectBytes` of the response body and are only evaluated when `behaviorScanResponseBody` is on. Action dispatch mirrors `_behavior_action_dispatch`: passive mode only logs the `[PASSIVE MODE]` lines, active mode bans with the rule's `ban_duration` or the 3600s fallback (reason `behavioral_violation`), alerts, or logs at the `log_suspicious_level`. `correlate_with_detection` halves the effective threshold for global return rules (min 1) while the IP has prior detection-category hits, driven by a new shared per-IP per-category suspicious-count store the `suspicious_activity` check writes (mirroring the reference reading `middleware.suspicious_request_counts`). Coverage lives in the new `bin/test_behavior.php` honesty runner (61 assertions porting the guard-core-go #26 engine-level matrix: config defaults and validation, the fail-closed scan check, inspect-bytes bounds, local and Redis-backed sliding windows (shared key layout pinned), the status:/json:/regex:/substring pattern surfaces, active/passive dispatch of all four actions, exclusion-scoped skips, engine-side usage tracking on allowed requests only, `processResponse` route and global return rules, correlation halving, endpoint ids, and the zero-rules zero-change pin) registered in the Makefile `RUNNERS`/`REDIS_RUNNERS` lists and the CI workflow.

Security headers management
---------------------------

### Added

- **Security headers management: the engine now computes the reference's default security header set and applies it to every blocked response.** Ported from guard_core `handlers/security_headers_handler.py` with the field defaults of `SecurityConfig.security_headers` (`_security_config_fields.py`), structurally following guard-core-go #22: the new `securityHeaders` config field accepts the reference-shaped block and defaults to enabled with the ten class-default headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 1; mode=block`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: geolocation=(), microphone=(), camera=()`, `X-Permitted-Cross-Domain-Policies: none`, `X-Download-Options: noopen`, COEP/COOP/CORP `require-corp`/`same-origin`/`same-origin`) plus `Strict-Transport-Security: max-age=31536000; includeSubDomains`. The `hsts` block builds `max-age`/`includeSubDomains`/`preload` with the reference preload corrections (preload requires max_age >= 31536000 and includeSubDomains, both logged since the PHP config has no warn channel), an ordered `csp` block joins directives into `Content-Security-Policy` ("directive source1 source2" joined with "; ", bare directives kept, unsafe sources logging the reference warning), the four override keys replace their headers when set (an absent or null override keeps the class default, the reference dict lookup returning None), `permissions_policy` is three-way (absent keeps the class default like the reference "UNSET" sentinel, an explicit null or empty string removes the header like the reference falsy check, any other value overrides it), and `custom` headers land last and may override anything. Validation is fail-closed at config construction like the reference `configure()` raising: RFC 7230 token names for custom headers, CRLF rejected, values capped at 8192 bytes, control characters sanitized away. Disabling the block (`securityHeaders: ['enabled' => false]`) removes every security header, matching `security_headers` falsy or `enabled: false` in the reference. The new `RenzoFranceschini\GuardCore\SecurityHeaders\SecurityHeadersPolicy` owns the logic and `GuardEngine::responseHeaders()` hands adapters the pass-through set to apply on the way out, mirroring the reference response factory's `process_response`. `with()` accepts the `security_headers` field and re-validates the copy. Coverage lives in the new `bin/test_security_headers.php` honesty runner (74 assertions porting the guard-core-go #22 engine-level matrix: the blocked-response default set, disabled pins, the pass-through API, the hsts preload corrections, ordered CSP builds, per-header overrides, custom-header precedence, fail-closed validation, CORS composition, fail-secure 500s, and `with()` immutability) registered in the Makefile `RUNNERS` list and the CI workflow.

--------------------

- **Log lines could carry raw control and non-ASCII bytes.** `LogActivity::buildMessage` interpolated redacted-but-unsanitized header, url, reason and trigger values, making line emission depend on the console encoding. Every assembled line is now pure printable ASCII (new `LogSanitizer`, port of the Python `_sanitize_for_log`): newline, carriage return and tab use the short escapes, every other control or non-ASCII code point becomes `\uXXXX`, and raw non-UTF-8 bytes (the surrogate-escape class of the Python engine) become `\xNN` (guard-core 4.0.4 parity, upstream commit f5d53ca5).
- **Deep-nested JSON in loggable values produced raw or half-redacted output.** When the JSON display-redaction depth cap trips (parse failure at the cap or traversal past it), the whole value now collapses to `[REDACTED]` instead of falling through to XML/pair redaction of the raw text; malformed JSON keeps falling through to those fallbacks (guard-core 4.0.4 parity, upstream commit 8bae9459).
- **Recon path rows flagged bare field values such as `?system=SAP` or `?file=README.md`.** Whole-value recon rows whose leading path separator is optional now require the scanned value to live in a path-like context (`url_path` or `unknown`) or to start with a path separator: `/default.asp` style probes still detect in every context, `url_path` behavior is unchanged, and the gate is keyed on the normalized context of the value actually being scanned (parity with guard-core PR #116, upstream commit 79818055). Regenerating the frozen conformance corpus at the post-#116 engine commit is a follow-up.

### Verification
